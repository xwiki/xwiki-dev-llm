# The xwiki-platform module structure

Which module a change belongs in is the first decision of most platform work, and the wrong answer
is expensive later: code in the wrong module either drags a dependency the module has no business
having, or lands in `oldcore` and has to be extracted again.

## The three top-level trees

```
xwiki-platform/
├── xwiki-platform-tools/         Maven build plugins and tools
├── xwiki-platform-core/          100+ feature modules — where development happens
│   ├── xwiki-platform-oldcore    the legacy core (com.xpn.xwiki.*), the central engine
│   └── xwiki-platform-<feature>  one per feature: rendering, security, livedata, …
└── xwiki-platform-distribution/  WAR packaging, the flavor, the functional tests
```

Nearly every change lands in `xwiki-platform-core/`. A change under `distribution/` is about what
ships and how it is assembled, and a change under `tools/` changes the build for every module at
once — treat both as wider-blast-radius than their size suggests.

## The modules worth knowing by name

| Module | What it is |
|---|---|
| `xwiki-platform-oldcore` | The central engine, `com.xpn.xwiki.*`. **Never add to it** — see below. |
| `xwiki-platform-rendering-*` | The content rendering pipeline. |
| `xwiki-platform-security-*` | Authentication, authorization, crypto. |
| `xwiki-platform-extension-*` | The extension / plugin management system. |
| `xwiki-platform-flamingo` | The default skin and theme. |
| `xwiki-platform-livedata` | The dynamic data-table UI component. |
| `xwiki-platform-ckeditor`, `xwiki-platform-blocknote` | The WYSIWYG editors. |

## New code goes in a feature module, never in oldcore

`oldcore` is what XWiki was before the split into domain modules, and the strategy is to keep
*extracting* code out of it — so a new class goes in the domain module that owns the concern, or in
a new module. The full rule, including which way the dependency may point and what happens when
oldcore turns out to need the new module, is in `component-system.md` under "Never grow
`xwiki-platform-oldcore`".

`XWikiContext` belongs to that legacy: it is a request-scoped object threaded through much of
oldcore, and new code reaches the same things through components instead of being handed a context.

## Every JAR is an OSGi bundle, and advertises what it provides

Each module's JAR carries an **OSGi manifest**, generated by the Maven Bundle Plugin configured once
in `xwiki-platform-core/pom.xml` — so a module does not declare its own, and a change to the shared
configuration affects every artifact.

A module tells the Extension Manager what it *provides*, beyond its own id, through the
`xwiki.extension.features` property in its pom. That is how one artifact can stand in for another —
a renamed module keeping its old id as a feature, or a `-legacy` variant standing in for the module
it re-exports — so an installed extension depending on the old id still resolves. Changing or
dropping a feature is therefore a compatibility change, not a rename.
